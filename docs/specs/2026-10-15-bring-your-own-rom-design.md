# Bring your own ROM (1.0.1)

Status: approved 2026-10-15 by a stand-in reviewer under the owner's delegation (approve
with changes; required changes 1-7 applied, the MD5 kept because the owner asked for it,
written by hand instead of the `md-5` crate).

## Goal

The tracked tree distributes none of the game, so the repository can go public. Every
Classic suite stays green on a machine with the ROM: the app, the tests, the oracle and
the disassembly all read the user's own ROM at run time. Two calls stay with the owner:
where CI gets a ROM, and the clean first public commit (section 9 prepares both, and the
palette's license). Nothing in this pass changes the game's behaviour.

## Success criteria

1. No tracked file contains a 32-byte run of the ROM's PRG or CHR
   (`tools/check-no-rom-data.py`), and no tracked file is a capture, rendering or archive
   of ROM data (the deletions in section 2: PNGs, the gzip tape, dumps).
2. With the ROM in `raw/`: `.orchestration/gates.sh` (with `ROTJ_REQUIRE_ROM=1`),
   `cargo deny check`, `disasm/assemble.sh` (`OK byte-identical`) and
   `tools/boot-check.sh` are green, and every test name in the 1.0.0 baseline run still
   runs (or is listed in the plan as merged into another test) and asserts as much.
3. Without the ROM: `cargo test --workspace`, clippy and fmt pass (ROM tests print
   `skipped`), and the app exits with status 2 and a message saying what to do.
4. The Windows build ships as the exe alone and plays from the owner's ROM.

The brief said "extract on first run into a cache dir". Nothing needs extracting: every
consumer wants a slice of PRG or CHR, and the whole ROM is 384 KiB, so the app slices it
in memory at start-up. The cache holds only the remembered ROM (section 3).

## 3. The loader: crate `rotj-rom`

One small crate, `crates/rotj-rom`, std only (MD5 is written out, about 40 lines, with the
RFC 1321 test vectors). `rotj-core`, `rotj-oracle`'s library and the app depend on it.
It cannot live in `rotj-core`: `rotj-core` dev-depends on `rotj-oracle`, so the oracle's
library depending on `rotj-core` would put two copies of `rotj-core` (and its ROM type)
in core's unit-test binary. It cannot live in `rotj-oracle`: the app would depend on test
tooling.

```rust
pub struct Rom { pub prg: Vec<u8>, pub chr: Vec<u8> }   // 128 KiB, 256 KiB

impl Rom {
    pub fn from_ines(bytes: &[u8]) -> Result<Rom, String>;   // mapper 69 checks, today's `Cart::from_ines`, plus the MD5
    pub fn load(arg: Option<&Path>) -> Result<Rom, String>;   // the app's search, below
}
pub fn for_test() -> Option<&'static Rom>;   // OnceLock; the tests' search and skip gate
```

**Check:** MD5 of PRG+CHR without the 16-byte header must be
`830111df30b8511562d4faca6aeb792d` (the iNES file's is `d229eab8…`; hashing without the
header accepts the same dump under another header). The error names the file, its MD5
and the expected one.

**The app's search** (`load`): the argument (dropping a ROM on the exe passes it), then
`ROTJ_ROM`, then the cache's `rom.nes`, then any `*.nes` beside the executable that
passes the check, then, in debug builds only (`cfg(debug_assertions)`), the workspace's
`raw/Batman - Return of the Joker (USA).nes`. An argument or `ROTJ_ROM` that names a
missing or wrong file is an error, not a skip; a bad cached or beside-exe file is noted
and the search goes on, so a corrupt cache cannot hide a good ROM (plan review). A ROM found through the argument or beside the exe
is copied to the cache (written to a temporary file, then renamed) so later launches find
it; if the cache is unwritable the game still runs. The cache is
`%LOCALAPPDATA%\batman-rotj` on Windows, else `$XDG_CACHE_HOME/batman-rotj` or
`~/.cache/batman-rotj`.

**The tests' search** (`for_test`): `ROTJ_ROM`, then `raw/`. Without either it prints
`skipped: no ROM (set ROTJ_ROM or put it in raw/)` and returns `None`; with
`ROTJ_REQUIRE_ROM` set it panics. A wrong ROM always panics. It replaces
`rotj_oracle::cart::{rom_path, load_rom}`, the gates in `replay::power_on`,
`machine::tests::rom`, `oracle.rs`'s `Scene` and `tas()`, `oam.rs`'s `prg()`, every test
`asset()`/`read_asset` that reads ROM bytes, and the oracle examples' `load_rom`/`rom_path`
(`bg_split`, `bg_chr`, `inventory`, `inventory_tas`, `routefind`, `replay`).
`rotj_oracle::Cart` becomes `rotj_rom::Rom`.

## 4. The app

`main` calls `Rom::load(args().nth(1))` before building the Bevy app and hands
`prg`/`chr` to `Play`, `Music::from_prg` and the APU's sample bank (`prg[0x1E000..]`,
bank 15). On error it prints one message and exits with status 2 without opening a
window:

```
Batman: Return of the Joker (USA) ROM not found.
Drop the .nes file onto batman-rotj.exe, put it next to the exe, or set ROTJ_ROM.
Looked in: …
```

On Windows (`cfg(windows)`, a console program) it then waits for Enter so a double-click
does not flash the message away. `assets_dir()`, `read_asset` and the `assets/` folder go
from the app; the palette is compiled in. `rotj_music::load_from_assets(dir)` becomes
`Music::from_prg(&prg)` (the same two slices).

## 5. Tests and fixtures

A converted test compares the same bytes as before. The rule for each fceux capture a test
reads:

1. Find the oracle run that reproduces it: the capture's own input, ported from its
   `dump.lua` mode and environment (`config.txt`) into a Rust input function and pokes,
   as `music.rs`'s `physics_input` and `run1`'s plan already are; or the TAS,
   `route-inputs.csv`, `stage1-inputs.csv`, `Scene::level`.
2. Before untracking the capture, commit its FNV-1a 64 digest (`tools/emu/digest.py`)
   and add an assertion that the oracle's bytes have that digest. The test then compares
   the port with the oracle's bytes, so a failure still names the byte.
3. If no oracle run reproduces the capture's bytes (for example a camera position only a
   lost input reached), the test moves to the nearest oracle scene of the same routine
   and the plan's fixture table marks it "compares different bytes", with what is lost.
   Those rows are reported to the owner.

The plan carries a fixture table: fixture, reader, oracle source, digest, same or
different bytes. Each conversion is checked once by breaking the code under test (or the
expected value) and seeing the test fail.

Specific cases:

- **Pure fceux anchors** (`run1.rs`: RAM every frame and APU writes; `route.rs`: RAM, OAM,
  APU at 900; `music.rs`: the physics capture's APU writes and driver calls; the title
  frame pixels, `reference-emulator-300.indices`): digests only, one per frame or per
  file. A mismatch names the frame and says to regenerate the capture with `dump.lua`.
- **Captures fed into the port as input**: `rotj-apu/tests/driver_trace.rs` and
  `rotj-music/tests/acceptance.rs` replay the APU-write CSV. They take the oracle's
  writes for the same run instead (anchored by `music.rs`'s digest), or are deleted when
  `rotj-oracle/tests/music.rs` already checks the same writes; the plan says which.
- **Dev-dependencies:** the app and `rotj-music`/`rotj-apu` gain `rotj-oracle` where a
  test needs it (no cycle: the oracle's library depends only on `rotj-rom`). Tests inside
  `rotj-core` use the crate's own `actor::oracle::Scene`. `rotj_core`'s `fnv1a` becomes
  public for the digests.
- **The state tape** moves to `target/tapes/` (per checkout, so worktrees cannot clash).
  The release lockstep writes it on every run instead of comparing with a committed copy.
  `the_tape_replays_the_chain` stays as a local speed-up (whole-game parity in a debug
  `cargo test` in seconds); it skips when the tape is absent, and under
  `ROTJ_REQUIRE_ROM` fails with the record command, so `gates.sh` runs the release
  `--ignored` suite (which records it) before the debug tests (plan review). Its old
  purpose, parity without a ROM, cannot survive: the port itself needs the ROM to run.
- **Untracking order:** a capture still read locally (for example `run1/ramseq-0.bin`)
  is untracked with `git rm --cached` and stays on disk (`tools/emu/*/` is already
  git-ignored); its digest is committed first. Captures nothing reads are untracked the
  same way. `assets/` gains a `.gitignore` entry for everything except
  `graphics/palette-sources/`, so `rotj-tools` and `tools/emu/sprites.py` keep writing
  their outputs there.

## 6. The disassembly

Untrack `disasm/*.s` and `disasm/rotj.cfg` (git-ignored). `generate.py` takes the ROM
path as an optional argument (default today's `raw/` path) and `assemble.sh` runs it
first with `$ROTJ_ROM` or the default, then assembles and compares with the same ROM.
`generate.py`, `observed_code.py`, `MAP.md` and `README.md` carry every label, table name
and annotation: regenerating today's tree reproduced all 20 committed files byte for byte
(checked 2026-10-15). The README says the `.s` are generated locally.

## 7. Pasted tables

Tables over 32 bytes are read from the ROM, and so are their partners in the same
function: `CLASS_RLE`, `CLASS_PTR`, `BODY_HANDLER`, `HEAD_TABLE` (`collision.rs`),
`AREA_PPU_TABLE` with `AREA_BANK_TABLE`, `CLASS_PPU_TABLE` with `CLASS_BANK_TABLE`
(`levelmap.rs`). The functions that use them gain a `prg` parameter:
`collision::{class_table, class_table_for_level, collision_of, Level::from_rom,
Level::loaded}`, `levelmap::{map_from_rom, attributes_from_rom}` and the class-table
reader at `levelmap.rs:421`, and their callers (`actor/room.rs:654`, `rotj-tools`, tests);
the plan lists each. `LEVEL_AREA_TABLE` (13), `AREA_SONGS` (18) and the DMC test records
(32) stay: a few bytes, as the PLAN allows. The port's own small constants (offsets, timers
like `k72.rs`'s) stay.

## 8. Tooling

- `tools/boot-check.sh` boots the app with the ROM; it also runs the exe with
  `ROTJ_ROM=/nonexistent` and expects status 2 and the message.
- `tools/check-no-rom-data.py`: fails if a tracked file contains a 32-byte window of the
  ROM's PRG or CHR (skipped without the ROM); runs in `gates.sh`.
- CI (public, no ROM): fmt, clippy, deny, build, `cargo test --workspace` (ROM tests skip)
  and the no-ROM boot check. The whole-game suites need a ROM (9.1).

## 9. Owner decisions (prepared, not taken)

### 9.1 Where CI gets a ROM

Without one, public CI checks formatting, lints, licenses, the build, the ROM-less tests
and the no-ROM boot. Most of the suite (every oracle, chain and picture test) skips, so a
green CI says little about parity. Options:

- **A. A private companion repo holding the ROM**, checked out in CI with a fine-grained
  read-only token stored as a secret, only on `push` to `main`, tags and manual dispatch
  (secrets never reach fork PRs). Runs the gates on GitHub's runners; the ROM sits in a
  private repo on GitHub. (A secret alone cannot hold it: secrets max out at 48 KB.)
- **B. A self-hosted runner on the owner's machine**, labelled `rom`, for the same events.
  The ROM never leaves the machine; the runner must be online, and a public repo's
  self-hosted runner must never take `pull_request` jobs.
- **C. No ROM in CI.** Parity stays a local gate (`gates.sh` at every merge and tag, as
  it has been since 0.1).

Recommendation: **C now, A when outside contributors appear.** Merges happen locally
through `gates.sh`, so CI parity adds nothing until someone else opens PRs; A is then
cheap to add and keeps runners off the owner's machine.

### 9.2 The clean first public commit

- **A. Orphan commit:** `git checkout --orphan public` at the 1.0.1 tree, one commit,
  pushed to a new public repo. This repo stays private with the full history, the tags
  0.1.1-1.0.1 and the release builds.
- **B. Rewrite history** with `git filter-repo`: drop the ROM-derived paths from every
  commit and blank pasted tables with `--replace-text`. Keeps the history for the
  methodology write-up, but every historical version of every file must be proved clean,
  and old commits would not build.

Recommendation: **A**, with the methodology write-up citing the private history. Before
it: `LICENSE-MIT`/`LICENSE-APACHE`, the `repository` URL, the cut-content essay's
provenance, whether `HANDOFF*.md`/`REPORT.md` go public, the palette (9.3), a README for
strangers, and `tools/check-no-rom-data.py` green on the tree.

### 9.3 The palette

FirebrandX publishes Composite Direct on his site with no license terms; Mesen, FCEUX and
MiSTer bundle it. (HANDOFF.md's "shipped with FCEUX under GPL" describes FCEUX's
distribution, not a grant from FirebrandX.) Options: keep it with attribution; ask
FirebrandX for permission; or ship a generated NTSC palette as Classic's default and load
a user's `.pal`. This pass changes nothing here. Recommendation: ask FirebrandX, keep it
with attribution if he agrees, otherwise the generated palette.
