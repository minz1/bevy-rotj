# Batman: Return of the Joker (USA) — 6502 disassembly

Mapper 69 (Sunsoft FME-7). Source ROM: `../raw/Batman - Return of the Joker
(USA).nes` (393,232 bytes; 16-byte iNES header + 128 KiB PRG + 256 KiB CHR;
SHA1 `668a395c…`). Reverse-engineering notes live in **`MAP.md`**.

## Quick start

    sh assemble.sh            # gen/generate.py, then ca65 + ld65 -> rotj.nes, byte-compared vs the ROM

The listing is not in the repository: it would be the game. `assemble.sh` generates it
from your own ROM (`$ROTJ_ROM`, else `../raw/`), so every label, table name and comment
lives in `gen/` (`generate.py`, `observed_code.py`) and in `MAP.md`. Run the generator as
`python3 gen/generate.py [rom]`, never with `python3 -I`: it imports `observed_code.py`
from its own directory, and without it the observed seeds are silently dropped.

`assemble.sh` prints `OK byte-identical (668a395c…)` when the built file equals
the original. That is the acceptance test and it passes. Override tool paths with
`$CA65` / `$LD65` (defaults to `~/.local/bin`). Object files land in `obj/`,
output in `rotj.nes`.

Files (all generated by `gen/generate.py`, and git-ignored, except this README,
`MAP.md`, `assemble.sh` and `gen/`):

- `header.s` — the 16 iNES header bytes, `.byte` listing, byte-for-byte.
- `bank00.s` .. `bank0F.s` — one 8 KiB PRG bank each (hex names), one ca65
  segment each.
- `chr.s` — the 256 KiB CHR `.incbin` straight from the source ROM (read-only
  at build time; the ROM is never written to), except CHR `$3DE60-$3FE5F`,
  which it includes from `cutscene.s`.
- `cutscene.s` — the 8 KiB of 6502 code and data that bank 2 `$99A9` copies from
  CHR into WRAM, listed by the same recursive descent from its two entries
  (`$6000`, the banner cutscene; `$6135`, the stage end) and assembled at its
  WRAM addresses with `.org` (`docs/ACTORS.md` §9o).
- `rotj.cfg` — ld65 memory/segment map (header + 16 PRG loads + CHR loads).

## What the generator does

Two passes, deterministic, one command:

1. **Recursive descent.** Start at the real entry points — bank 15's `$FFFA`
   vectors: `reset_entry $E2E6`, `nmi_entry $E1D0`, `irq_entry $E2A9` — plus the
   targets of two literal jump tables in the fixed bank (`$E076`, `$E2CA`).
   Follow `JSR`/`JMP`/branches; mark every reached byte as code and every reached
   `JSR`/branch target as a label. Far calls (leaving the bank's window) are
   resolved through the FME-7 window map (`DEFAULT_WINDOWS`, observed at reset)
   and seed entry points in the switchable banks; this iterates until it settles.
   A bank with no known entry keeps the historic linear-sweep listing.
2. **Emit.** Instructions where the descent proves code, grouped `.byte` runs
   everywhere else, labels for proven targets, `; PPU…/APU…/FME-7` comments for
   recognised I/O ports, and labelled `tbl_*` blocks for the data tables listed
   in `gen/generate.py` (`TABLES`) — see `MAP.md`.

Byte-identity is structural: any byte the emitter is unsure about is a `.byte`,
and an instruction is only emitted when all its bytes belong to it. Re-running
is stable (no timestamps, no nondeterministic ordering).

## Bank / window convention

FME-7 has three switchable 8 KiB windows (`$8000`, `$A000`, `$C000`), a `$6000`
window, and a fixed `$E000` window (last PRG bank 15). Because ca65 needs a
fixed run address per segment, `rotj.cfg` gives every bank a deterministic "run"
window (label space only, `file = ""`). `style_windows()` in the generator uses
each bank's **observed** code window where RE could prove it (bank 02 at
`$8000`, bank 0D at `$A000`, bank 0E at `$C000`, bank 15 at `$E000`, …) and the
historic `bank % 3` rotation for the banks with no decisive self-reference. The
full table and its evidence are in `MAP.md` §1.

Bytes are laid out physically in ROM order (`LOAD0..15` then `CHR`), so ld65's
output is the full iNES file: 16 header + 16×8192 PRG + 262144 CHR.

## Labels and data

- `reset_entry`/`nmi_entry`/`irq_entry` and `irq_*`/`far_*`/`sub_*`/`loc_*`/
  `tbl_*` labels are emitted where the byte stream proves the target.
- Cross-window `JSR`/`JMP` stay numeric (`a:$XXXX`) with a `; far …` comment.
- `JMP (ind)` gets a "target unknown at build" comment.
- Unreached bytes are `.byte`; runs of ≥3 equal bytes are grouped.
- Data tables found during RE are emitted as labelled, grouped `.byte` blocks
  with a `;` note (`tbl_e076`, `tbl_irq_split`, `tbl_8000_ptr`, `tbl_song_ptr`,
  `tbl_9beb_ppulist`, `tbl_91b7_ppulist`).

## Known limitations / next steps

1. Banks 0B, 0C, 0D and the fixed 0F have entry points reached from the
   vectors / IRQ table / cross-bank far calls; the rest rely on the FME-7
   window-map seeding or keep the linear fallback. A stage-table trace would
   seed the remaining stage banks from observed data (§9 of `MAP.md`).
2. Mid-frame `$D3` split-handler indices beyond the clean ones are unproven
   (some `$E2CA` slots are `$FF` padding or mid-instruction).
3. Per-stage palette/level assignment is not isolated; the palette *mechanism*
   and candidate tables are documented, not the per-scene mapping.
4. The `IRQ` handler is real (`$E2A9`), not unused — see `MAP.md` §3.
5. In the linear-fallback banks a misplaced decode is still possible (the sweep
   can start decoding data as code); such bytes reproduce exactly but may not be
   the real instruction stream.

Build artifacts `obj/` and `rotj.nes` are intermediate; regenerating overwrites
only generated files (safe, idempotent).
